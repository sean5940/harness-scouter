# Harness Scouter 설계

작성일: 2026-07-29

## 1. 문제

개발자가 coding agent로 작업할 때, 결과 품질은 프롬프트·컨텍스트·하네스·루프 설계에 따라 크게 갈린다. 그런데 그 설계가 좋아지고 있는지 나빠지고 있는지 판단할 근거가 없다. 훅을 추가하고 스킬을 고치지만 효과는 감으로만 안다.

Claude Code는 모든 세션을 `~/.claude/projects/<encoded-cwd>/<session-id>.jsonl`에 남긴다. 이 기록에서 관측 가능한 신호를 뽑아 하네스 설계 품질을 추적하는 것이 이 도구의 목적이다.

이름은 측정기 은유에서 왔다. 대상은 agent 자체가 아니라 agent를 감싸는 하네스다.

## 2. 실측 근거

설계 전 실제 코퍼스를 조사했다. 표본은 300KB 이상 세션 파일 276개, 224,678라인이다. 전체 코퍼스는 1,459파일 899MB다.

측정 가능한 것으로 확인된 신호:

| 신호 | 표본 실측 | 용도 |
|---|---|---|
| `toolDenialKind: user-rejected` | 27 | 사용자가 도구 호출을 거부 |
| `toolDenialKind: permission-rule` | 1,010 | 훅·권한 규칙이 차단 |
| `Request interrupted by user` | 126 | 사용자가 실행 중 중단 |
| `tool_result.is_error: true` | 1,859 (성공 12,979) | 도구 실패율 약 12.5% |
| `usage.cache_read` / `cache_creation` | 응답마다 | 컨텍스트 재사용 효율 |
| `attributionSkill` | 상위 15종 집계 | 세션을 작업 유형별로 층화 |
| `file-history-delta.trackingPath` | 1,342 | 같은 파일 재편집 = 재작업 |
| `pr-link` | 3,946 (중복 포함) | 산출물 도달 |
| Bash 명령 전문 | 56,145 | tsc 754 / eslint 657 / test 119 / commit 500 |

### 2.1 키워드 기반 감정 분석은 폐기한다

사용자 메시지에서 교정 신호를 뽑는 접근을 실제로 시도했다. 사용자 메시지 17,194건에 대한 결과:

```
"아니"      486   대부분 "아니라 / 아니면" 접속사
"말고"      207   대부분 정상 지시문
"다시"      190   "다시 확인해줘" 등 중립
"틀렸"        3
"빠졌"        2
"그게 아니"   2
"좋아"        2   만족 신호는 사실상 잡히지 않음
```

명백한 교정 신호는 한 자릿수에서 수십 건인데 노이즈는 수백 건이다. 정규식·키워드 스코어링은 이 데이터에서 작동하지 않는다. 이 경로는 설계에서 제외한다.

## 3. 설계를 지배하는 함정 세 가지

### 3.1 "agent의 능력"이라는 단일 측정 대상은 없다

관측 결과는 네 요소의 곱이다.

```
관측 결과 = 모델 능력 × 하네스·스킬 설계 × 프롬프트 × 작업 난이도
            (통제 불가)   (통제 가능)      (통제 가능)  (통제 불가, 점수를 지배)
```

개선하려는 대상은 가운데 둘인데 점수를 가장 크게 흔드는 것은 작업 난이도다. 보정하지 않으면 "이번 주에 쉬운 일을 했다"를 "설계가 좋아졌다"로 읽게 된다.

**방어**: 절대점수를 쓰지 않는다. `attributionSkill`로 세션을 작업 유형별로 묶고, 같은 층 안에서 자기 이력 대비 백분위만 낸다.

한 세션에 스킬이 여러 개 찍히는 경우가 많으므로 층 배정 규칙을 정해 둔다. 그 세션에서 호출 수가 가장 많은 스킬을 대표 층으로 삼고, 스킬이 하나도 없으면 `unattributed` 층에 넣는다. 대표 스킬의 비중이 절반에 못 미치면 `mixed` 층으로 뺀다. 성격이 섞인 세션을 특정 층에 우겨넣으면 그 층의 분포가 오염되기 때문이다.

### 3.2 굿하트의 법칙이 유독 강하게 작용한다

이 도구의 사용자는 측정 대상을 직접 고치는 사람이다. `CLAUDE.md`와 훅을 본인이 쓴다. 측정과 개입 사이 거리가 짧을수록 지표는 빨리 무의미해진다. "검증 성실도"가 낮게 나오면 규칙을 넣게 되고, agent는 의미 없이 tsc를 돌리고, 축은 커지는데 품질은 그대로다.

**방어**: 지표마다 조작 저항 등급을 붙이고 저항이 낮은 지표의 가중치를 낮춘다. 뷰 C는 "지표가 올랐는가"가 아니라 "올리는 동안 다른 축이 떨어지지 않았는가"를 본다.

### 3.3 정답 라벨이 없다

세션이 좋았는지 나빴는지에 대한 라벨이 없다. 유추 경로 하나(키워드)는 2.1에서 이미 무너졌다.

**방어**: M1.5에 수동 라벨링 게이트를 강제로 넣는다. 지표가 라벨과 상관되지 않으면 폐기한다.

## 4. 아키텍처

### 4.1 패키지 분리

경계 기준은 "VSCode 없이 테스트 가능한가"다.

| 패키지 | 책임 | VSCode 의존 |
|---|---|---|
| `core` | JSONL 증분 파싱 → SQLite, 지표 계산 | 없음 |
| `cli` | `scouter scan` / `diag` / `json` | 없음 |
| `ext` | 상태바, Webview, 세션 점프 | 있음, 얇게 |

`ext`는 `cli`를 자식 프로세스로 실행해 JSON을 받는다. 지표 계산이 확장 코드에 들어가면 테스트가 Extension Host 위에서만 돌게 되므로 금지한다.

### 4.2 데이터 흐름

```
JSONL 1,459파일
  ↓ [1] 증분 파서 (파일별 mtime + byte offset)
[2] 사실 테이블 (SQLite)      ← SSoT. 해석을 담지 않는다
  ↓ [3] 지표 계산기 (순수 함수)
  ↓ [4] 층화기 (attributionSkill / cwd / 기간)
  ├─→ 뷰 B 누수 진단기
  ├─→ 뷰 A 스코어카드
  └─→ 뷰 C 개입 효과 측정기
```

`[2]`에 점수를 넣지 않는 이유는 지표 정의가 앞으로 계속 바뀌기 때문이다. 정의를 바꿀 때마다 899MB를 재파싱하면 반복 주기가 무너진다.

### 4.3 데이터 모델

```sql
file_cursor(path PK, mtime_ms, byte_offset, parsed_at)
session(session_id PK, project, git_branch, started_at, ended_at,
        model, cc_version, skills_json)
turn(session_id, uuid, role, ts, has_thinking, tool_count)
tool_call(session_id, uuid, name, is_error, denial_kind, ts)
file_edit(session_id, tracking_path, ts, message_id)
artifact(session_id, kind, ref, ts)
usage(session_id, message_id, input, output, cache_read, cache_creation, ts)
```

파서는 방어적으로 동작한다. 모르는 필드는 무시하고 없는 필드는 null로 둔다. Claude Code가 업데이트되면 스키마가 바뀌므로 `cc_version`을 세션마다 기록해 나중에 버전별 차이를 구분할 수 있게 한다.

JSONL은 append-only라 증분 파싱이 깔끔하게 성립한다. 파일 크기가 줄었거나 mtime이 역행하면 해당 파일만 전체 재파싱한다.

## 5. 지표

### 5.1 신호 계층

| 계층 | 성격 | 비용 | 첫 버전 |
|---|---|---|---|
| Tier 1 | 결정적. 라벨 불필요, 조작 어려움 | 0 | 포함 |
| Tier 2 | 구조적. 계산 가능하나 해석 필요 | 0 | 포함 |
| Tier 3 | 의미적. LLM 판정 필요 | 높음 | 제외 |

Tier 3 전수 판정은 899MB에 대해 비현실적이다. 나중에 넣더라도 층화 표본에만 적용한다.

### 5.2 축 정의

| 축 | 계산 | 조작 저항 |
|---|---|---|
| 자율 완주력 | `1 − (interrupt + user_rejected) / 100턴` | 높음 |
| 첫 시도 정확도 | `1 − 동일 tracking_path 재편집률`, tool error rate 결합 | 중간 |
| 검증 성실도 | 커밋 직전 N턴 안에 tsc·lint·test가 있었던 비율 | 낮음 |

N의 초기값은 10으로 두고 M1.5에서 라벨과의 상관을 보며 조정한다. 창이 너무 좁으면 배치 커밋을, 너무 넓으면 무관한 검증을 잡는다.
| 컨텍스트 절제 | `cache_read / (cache_read + cache_creation)`, 중복 Read | 중간 |
| 규칙 준수 | `permission-rule` 차단 빈도 | 위험, 5.3 참조 |
| 결과 도달 | 세션당 commit·PR 생성 (중복 제거 후) | 중간 |

### 5.3 규칙 준수 축의 역설

훅 차단은 "agent가 규칙을 어기려 했다"는 신호다. 그런데 훅을 지우면 어겨도 잡히지 않으므로 점수가 올라간다. 방어를 없앨수록 좋아 보이는 값은 지표로 쓸 수 없다.

훅 커버리지로 정규화하거나 축에서 제외한다. M1.5 폐기 후보 1순위로 둔다.

### 5.4 육각형 축 배치

레이더 차트를 쓸 경우 상충하는 축을 마주보게 배치한다.

- 자율 완주력 ↔ 검증 성실도
- 컨텍스트 절제 ↔ 첫 시도 정확도

"넓을수록 좋다"는 착시 대신 "설계가 어느 쪽으로 치우쳤는지"가 읽히게 하려는 배치다. 두 쌍은 실제로 트레이드오프이고 정답은 작업 유형마다 다르다.

## 6. 뷰

세 뷰는 같은 지표 계산기를 공유하며 표현만 다르다.

| 뷰 | 답하는 질문 | 표현 |
|---|---|---|
| B 누수 진단기 | 어디서 새는가 | 임계 초과 항목 + 근거 세션 ID |
| A 스코어카드 | 어느 방면이 강하고 약한가 | 층내 백분위 육각형 |
| C 개입 효과 | 내가 넣은 훅·스킬이 효과가 있었나 | 지표 시계열 × config 커밋 시점 |

뷰 C는 config 레포(`sean-soomgo-ai-config`)의 커밋 타임스탬프와 세션 타임스탬프를 정합해 도입 전후를 비교한다. 예: "특정 훅 도입 후 4주간 탐색 위임률 31% → 58%, 세션당 토큰 12% 증가."

## 7. 화면 표면

1단계는 상태바와 패널까지다.

```
상태바   한 줄 요약, 클릭하면 패널
Webview  육각형 / 진단 목록 / 추이
점프     근거 세션을 클릭하면 해당 파일·커밋으로 이동
```

Webview는 CSP 때문에 외부 CDN을 불러올 수 없다. 차트는 번들에 포함하거나 SVG로 직접 그린다. 축 6개짜리 레이더는 직접 그리는 편이 짧다.

파싱은 Extension Host에서 돌리지 않는다. 자식 프로세스로 분리한다.

## 8. 마일스톤

```
M0    파서 + SQLite. 뷰 없음
M1    CLI 진단 (뷰 B). 터미널 출력
M1.5  타당성 게이트 (필수)
M2    VSCode 확장 (뷰 A). 상태바 + Webview
M3    뷰 C
M4    실시간 tail
```

### M1.5 타당성 게이트

M2로 넘어가기 전에 반드시 통과해야 한다.

1. 세션 30개를 수동으로 좋음/나쁨 라벨링한다. 본인이 당사자라 기억이 남아 있는 동안 해야 한다.
2. 각 지표가 라벨과 상관되는지 확인한다.
3. 상관이 없는 지표는 폐기한다.

축이 3개만 남아도 진행한다. 6개를 채우려고 억지 지표를 만들지 않는다. 검증 없이 M2로 가면 예쁘지만 의미 없는 육각형이 나오고, 그 상태를 되돌리는 비용이 훨씬 크다.

## 9. 알려진 사각지대

측정하지 못하는 것을 문서에 남긴다. 나중에 지표로 착각하지 않기 위해서다.

- **subagent 내부 턴이 기록되지 않는다.** 표본에서 `Agent` 호출은 539건인데 `isSidechain`은 전부 false였다. 위임 비중이 큰 워크플로일수록 커버리지가 떨어진다. 지표로 보정할 수 없으므로 세션마다 커버리지를 함께 표시한다.
- **세션 경계와 작업 경계가 다르다.** 한 세션에 여러 작업이 들어가고 한 작업이 여러 세션에 걸친다. `attributionSkill`과 `git_branch`로 묶는 것이 최선이며 완전하지 않다.
- **`pr-link`가 중복 기록된다.** 같은 PR이 한 세션에 여러 번 찍힌다. 중복을 제거하지 않으면 결과 도달 축이 부풀려진다.

## 10. 비목표

- 팀 비교, 리더보드, 타인과의 순위. 사용자가 한 명이므로 외부 벤치마크가 없다.
- 절대점수 표기. 층내 백분위만 쓴다.
- Claude Code 외 다른 agent 도구 지원.
- Tier 3 LLM 판정. 첫 버전 범위 밖이다.
- 실시간 모니터링. M4까지 다루지 않는다.
