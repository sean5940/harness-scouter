# Harness Scouter 설계

작성일: 2026-07-29
개정: 2026-07-30 (v5 — M0.5 게이트 결과와 뷰 B 축소 결정)

## 0. 이 문서의 신뢰 등급 표기

축과 수치에는 아래 등급을 붙인다. 등급 없는 수치를 인용하지 않는다.

| 표기 | 뜻 |
|---|---|
| `[검증]` | 코퍼스에서 직접 재계산해 확인함 |
| `[후보]` | 한 번만 측정됐고 재현 확인 전 |
| `[미검증]` | 정의만 있고 측정 안 됨 |

v2에서 이 등급 체계를 도입한 이유는 v1의 수치 중 여러 개가 재현되지 않았기 때문이다. 자세한 것은 5.5절.

## 0.1 현재 상태 (v5)

**M0.5 재현성 게이트를 확정 6축에 돌린 결과는 0/6 통과다.** 그래서 제품 범위를
**뷰 B(누수 진단) 하나로 좁힌다.** 뷰 A(육각형 스코어카드)와 뷰 C(개입 효과)는
축이 게이트를 통과할 때까지 보류한다. 근거와 수치는 8.1절.

계측 인프라는 유지한다 — 파서·사실 테이블·정의 고정·게이트는 그대로 쓰고,
그 위에 얹는 표현만 진단으로 한정한다.

## 1. 문제

개발자가 coding agent로 작업할 때, 결과 품질은 프롬프트·컨텍스트·하네스·루프 설계에 따라 크게 갈린다. 그런데 그 설계가 좋아지고 있는지 나빠지고 있는지 판단할 근거가 없다. 훅을 추가하고 스킬을 고치지만 효과는 감으로만 안다.

Claude Code는 모든 세션을 `~/.claude/projects/<encoded-cwd>/<session-id>.jsonl`에 남긴다. 이 기록에서 관측 가능한 신호를 뽑아 하네스 설계 품질을 추적하는 것이 이 도구의 목적이다.

이름은 측정기 은유에서 왔다. 대상은 agent 자체가 아니라 agent를 감싸는 하네스다.

## 2. 실측 근거

표본은 300KB 이상 세션 파일 276개, 224,678라인이다. 전체는 `.jsonl` 1,471개 913MB인데, 그중 **메인 세션은 452개**이고 나머지 약 1,019개는 subagent·워크플로 기록이다 `[검증]`. v3까지 "세션 1,485개"로 적은 것은 파일 수를 세션 수로 오인한 것이다.

| `toolDenialKind: user-rejected` | 27 `[검증]` | 이벤트 희박 |
| `Request interrupted by user` | 126 `[검증]` | **축 불가** — 277세션 중 218개(78%)가 0회 `[검증]` |

### 2.1 키워드 기반 감정 분석은 폐기한다

사용자 메시지에서 교정 신호를 뽑는 접근을 시도했다. 메시지 17,194건에 대한 결과:

```
"아니"      486   대부분 "아니라 / 아니면" 접속사
"말고"      207   대부분 정상 지시문
"다시"      190   "다시 확인해줘" 등 중립
"틀렸"        3
"빠졌"        2
```

명백한 교정 신호는 한 자릿수에서 수십 건인데 노이즈는 수백 건이다. 정규식·키워드 스코어링은 이 데이터에서 작동하지 않는다.

## 3. 설계를 지배하는 함정

### 3.1 "agent의 능력"이라는 단일 측정 대상은 없다

관측 결과는 네 요소의 곱이다.

```
관측 결과 = 모델 능력 × 하네스·스킬 설계 × 프롬프트 × 작업 난이도
            (통제 불가)   (통제 가능)      (통제 가능)  (통제 불가, 점수를 지배)
```

**방어**: 절대점수를 쓰지 않는다. v2 초안은 "층내 자기이력 대비 백분위"였으나 데이터 기간이 짧아 성립하지 않는다. 3.4절에서 delta 비교로 바꾼다.

#### 층화 규칙 (v2에서 재설계)

v1은 `attributionSkill`을 1차 층으로 삼았다. 이 규칙은 검증에서 깨졌다.

- v1 배정 규칙(최다 스킬 50% 미만이면 `mixed`)을 적용하니 204세션 중 **168개(82%)가 `mixed` 한 덩어리**, 층 설명력 eta² 0.078 `[후보]`
- `end_turn` 2,916건 중 **2,193건(75.2%)이 `attributionSkill` 없음** `[후보]` — 세션의 상당 부분이 스킬 컨텍스트 밖에서 일어난다
- 자율 구간 길이 축에서 실행 모드 eta² 0.543 > `attributionSkill` 0.307 `[후보]`

**v2 층화**: 1차 = 실행 모드(headless / 대화형), 2차 = 산출물 종류(코드 편집 / 문서 편집 / 시각 QA 포함), 3차 = `attributionSkill`.

**단, 이 층화는 지금 검증 불가다.** `entrypoint` 필드가 표본 276세션 중 `claude-vscode` 274 / `sdk-cli` 2로 사실상 한 값이다 `[후보]`. **headless 층이 존재하지 않으므로 현재 6축 전부가 대화형 층에서만 검증됐다.** M1 전에 `ultra-implement` 같은 무인 워커 세션을 의도적으로 축적해야 한다. 실행 모드 판별자는 첫 사용자 메시지의 `promptSource`와 워커 프롬프트 지문으로 만들되, 스킬 문구가 바뀌면 깨진다는 점을 파서 주석에 남긴다.

### 3.2 굿하트의 법칙이 유독 강하게 작용한다

이 도구의 사용자는 측정 대상을 직접 고치는 사람이다. `CLAUDE.md`와 훅을 본인이 쓴다. 측정과 개입 사이 거리가 짧을수록 지표는 빨리 무의미해진다.

**방어 세 겹**:
1. 지표마다 조작 저항 등급을 붙이고 저항이 낮은 지표의 가중치를 낮춘다.
2. 대립쌍을 마주보게 배치해 한 축을 올리면 짝이 내려가게 한다 (5.4).
3. 뷰 C는 "지표가 올랐는가"가 아니라 "올리는 동안 다른 축이 떨어지지 않았는가"를 본다.

검증 2라운드가 반복해서 보여준 명제 하나를 여기 남긴다 — **가장 싼 개선책은 대개 조작이다.** 그래서 5.6절의 성장 가이드는 "할 것"마다 "하지 말 것"을 짝지어 적는다.

### 3.3 정답 라벨이 없다

세션이 좋았는지 나빴는지에 대한 라벨이 없다. 유추 경로 하나(키워드)는 2.1에서 무너졌다.

**방어**: 수동 라벨링 게이트를 M1 앞으로 당긴다 (8절).

### 3.4 집계 단위가 양쪽에서 막힌다

축을 다 정하고 나서야 드러난 함정이다. **세션 단위는 분모가 비고, 시간 단위는 표본이 빈다.**

세션당 분모 실측 `[검증]`:

```
축2 Read       13.0/세션  ┐
축5a 편집       9.0/세션  │ 세션 단위로 충분
축4 verifier    6.0/세션  ┘
축1 큰파일      3.0/세션  ┐
축5b 탐색       2.0/세션  │ 세션 단위로 부족 (M0.5 게이트 3번 미달)
축3 코드커밋    0.7/세션  ┘ 최약축. 세션의 55%에 아예 없음
```

축마다 밀도가 20배 가까이 차이난다. 그렇다고 시간으로 묶으면 표본이 사라진다 — 전체 코퍼스가 **2026-06-26부터 약 5주치**이고 활동일이 29일이라 주 단위로 6구간밖에 안 나온다 `[검증]`. 전수 파싱을 해도 이건 안 풀린다. 메인 세션은 276 → 452로 1.6배이고 **기간은 그대로다** `[검증]`. 실제로 전수 스캔 후 구간은 30개가 나왔다.

#### 집계 단위 = 이벤트 예산 구간

세션을 시간순으로 쌓다가 **6축 전부가 최소 분모를 채우는 지점**에서 끊는다. 구간 길이는 시간이 아니라 이벤트가 정한다.

```
예산 벡터: 축1 ≥ 10 / 축2 ≥ 20 / 축3 ≥ 10 / 축4 ≥ 10 / 축5a ≥ 20 / 축5b ≥ 10
상한 폴백: 40세션에 도달하면 예산 미달이어도 구간을 닫고, 미달 축은 회색 처리
```

6축이 **같은 구간**을 보므로 육각형 한 장의 시점이 일관된다. 축마다 다른 범위를 보게 하는 방식(축1은 최근 3세션, 축3은 최근 14세션)은 한 장의 그림에 시점이 섞여 판독이 불가능하므로 쓰지 않는다.

표본 275세션으로 시뮬레이션한 결과 `[검증]`:

```
275세션 → 구간 24개, 전부 예산으로 닫힘 (상한 폴백 0회)
구간 크기 2~28세션 / 1~7일
binding 축은 구간마다 바뀜 (축1이 걸리는 구간과 축3이 걸리는 구간이 섞임)
```

구간 크기 편차가 크므로 **축 값 옆에 그 구간의 분모를 함께 표시**한다. 비율 지표라 분모가 크면 더 안정적이지만, 구간 간 분산이 달라지므로 분모를 숨기면 작은 구간의 튐을 실제 변화로 오독한다.

#### 표시는 백분위가 아니라 delta

구간이 24개(전수 40개 예상)뿐이고, 이를 실행 모드 × 산출물 종류로 층화하면 층당 한 자릿수가 된다. **백분위는 성립하지 않는다.**

대신 **직전 3구간 중앙값 대비 변화**를 표시한다. 비교 대상이 2개만 있어도 성립하고, 이 연산이 뷰 C(개입 효과)와 동일하므로 뷰 A와 뷰 C가 같은 계산을 공유한다.

부수 효과로 굿하트 방어가 강해진다. 백분위는 "평소보다 잘했나"라 조작하면 바로 오르지만, delta는 개입 전후를 보므로 **한 축을 올리는 동안 다른 축이 떨어졌는지**가 같은 화면에 남는다. 3.2절 방어 3번이 뷰 C 전용이 아니라 기본 표시 방식이 된다.

데이터가 쌓여 구간이 100개를 넘으면 백분위로 승격할 수 있다. 그때까지는 delta만 쓴다.

## 4. 아키텍처

### 4.1 패키지 분리

경계 기준은 "VSCode 없이 테스트 가능한가"다.

| 패키지 | 책임 | VSCode 의존 |
|---|---|---|
| `core` | JSONL 증분 파싱 → SQLite, 지표 계산 | 없음 |
| `cli` | `scouter scan` / `diag` / `json` | 없음 |
| `ext` | 상태바, Webview, 세션 점프 | 있음, 얇게 |

`ext`는 `cli`를 자식 프로세스로 실행해 JSON을 받는다. 지표 계산이 확장 코드에 들어가면 테스트가 Extension Host 위에서만 돌게 되므로 금지한다.

### 4.2 데이터 흐름

```
JSONL 1,459파일
  ↓ [1] 증분 파서 (파일별 mtime + byte offset)
[2] 사실 테이블 (SQLite)      ← SSoT. 해석을 담지 않는다
  ↓ [3] 지표 계산기 (순수 함수)
  ↓ [4] 층화기 (실행모드 / 산출물종류 / attributionSkill)
  ├─→ 뷰 B 누수 진단기
  ├─→ 뷰 A 스코어카드
  └─→ 뷰 C 개입 효과 측정기
```

`[2]`에 점수를 넣지 않는 이유는 지표 정의가 계속 바뀌기 때문이다. 정의를 바꿀 때마다 899MB를 재파싱하면 반복 주기가 무너진다.

### 4.3 데이터 모델

```sql
file_cursor(path PK, mtime_ms, byte_offset, parsed_at)
session(session_id PK, project, git_branch, started_at, ended_at,
        model, cc_version, entrypoint, exec_mode, skills_json)
turn(session_id, uuid, role, ts, has_thinking, tool_count)
tool_call(session_id, uuid, seq, name, is_error, denial_kind, ts,
          input_json)          -- Bash command / Read file_path·offset·limit 보존
tool_result(session_id, uuid, total_lines, num_lines, start_line,
            stdout_tail)       -- 축1 no-op 가드, 축4 stdout 판정에 필요
file_edit(session_id, tracking_path, ts, message_id)
artifact(session_id, kind, ref, ts)
usage(session_id, message_id, request_id, input, output,
      cache_read, cache_creation, ts)
```

v1 대비 추가한 것: `tool_call.seq`(축3의 순서 판정), `tool_result.total_lines`(축1의 no-op 가드), `stdout_tail`(축4의 성패 판정), `usage.request_id`(중복 제거 — 69,648행 중 고유 27,470으로 2.53배 중복 의심 `[후보]`).

파서는 방어적으로 동작한다. 모르는 필드는 무시하고 없는 필드는 null로 둔다. `cc_version`을 세션마다 기록해 버전별 스키마 차이를 구분한다.

JSONL은 append-only라 증분 파싱이 성립한다. 파일 크기가 줄었거나 mtime이 역행하면 그 파일만 전체 재파싱한다.

## 5. 지표

### 5.1 신호 계층

| 계층 | 성격 | 첫 버전 |
|---|---|---|
| Tier 1 | 결정적. 라벨 불필요, 조작 어려움 | 포함 |
| Tier 2 | 구조적. 계산 가능하나 해석 필요 | 포함 |
| Tier 3 | 의미적. LLM 판정 필요 | 제외 |

### 5.2 축 정의 (v2 확정)

| # | 축 | 답하는 질문 | 계산 | 조작저항 | 등급 |
|---|---|---|---|---|---|
| 1 | 읽기 범위 규율 | 큰 파일을 통째로 읽지 않았나 | `partial_reads / reads`, 분모는 `totalLines>200`인 Read | 중 | `[검증]` |
| 2 | 읽기 왕복 절제 | 같은 파일을 이유 없이 다시 읽지 않았나 | `1 − 동일 file_path 재Read / 전체 Read` | 중 | `[검증]` |
| 3 | 검증 신선도 | 검증이 마지막 편집 **이후**에 돌았나 | 커밋 segment에서 `idx(마지막 verifier) > idx(마지막 편집)` 비율 | **낮음** | `[후보]` |
| 4 | 검증 공회전 절제 | 편집 없이 같은 검증을 반복하지 않았나 | `1 − 편집 없는 블록 내 동일 verifier 재실행 / 전체 verifier` | 중 | `[후보]` |
| 5a | 계측 채널 준수 | 읽기와 **쓰기**를 계측 도구로 했나 | `1 − (bash 읽기 + bash 쓰기) / (그것 + Read + Edit + Write)` | **높음** | `[미검증]` |
| 5b | 인덱스 우선 탐색 | 재귀검색 대신 qmd·graphify를 먼저 썼나 | `1 − (bash 재귀검색 + Grep + Glob) / (그것 + qmd + graphify)` | 중 | `[후보]` |

#### 축별 정의 세부

**축1 — no-op 가드가 정의의 핵심이다.** `Read`의 기본 동작이 최대 2000줄이므로 `limit: 2000`은 완전한 no-op인데 부분읽기로 집계된다. `limit >= totalLines - offset`이거나 결과가 `numLines >= totalLines && startLine <= 1`이면 부분읽기로 인정하지 않는다. 이미지·바이너리(`.png` `.jpg` `.pdf` `.ipynb`)는 분모에서 뺀다.

크기 구간별 부분읽기율이 200줄에서 꺾인다 `[후보]`: 20.5%(≤200) / 71.6%(201-500) / 96.7%(501-2000) / 95.7%(>2000). 임계 200줄은 이 관측에서 왔다.

**축2 — v1의 정의와 수치가 어긋나 있었다. 정의를 SSoT로 삼는다.**

```
배제 미적용:  865/5,202 = 16.63%   ← v1이 문서에 적은 수치
배제  적용:  464/5,202 =  8.92%   ← v1이 문서에 적은 정의대로 계산한 값
```

둘 다 `[검증]`이다. v1 산문은 "직전 Read 이후 그 경로에 Edit/Write가 있었으면 정당한 재확인이므로 제외"라고 썼는데 숫자는 제외를 적용하지 않은 값이었다. **정의를 SSoT로 하고 기준값을 8.92%로 정정한다.**

**축3 — "돌렸는가"가 아니라 "최종 상태가 검증됐는가"다.** v1은 "커밋 직전 N턴 안에 검증이 있었나"였는데, 그러면 검증한 뒤에 또 고치고 커밋한 경우를 잡지 못한다. 코드 커밋의 31.0%가 이 stale 상태다 `[후보]`. 창 크기 N 튜닝이 불필요해지는 것은 부수 효과다.

분모는 **코드 확장자 편집이 있는 커밋만**이다. 문서 커밋 100건은 none이 87%라 `[후보]` 분모를 제한하지 않으면 축이 붕괴한다. `git commit --amend`는 제외하고, 편집 0건 커밋은 커버리지 구멍으로 별도 표기한다.

**축4 — 성패 판정에 `is_error`를 쓰지 않는다.** Bash 에러 중 상당수가 tsc/eslint의 정보성 비영 종료다 `[후보]`(한 측정에서 423건 중 198건, 다른 측정에서 1,270건 중 256건). 게다가 검증 호출의 71%가 `| tail`로 exit code를 삼킨다 `[후보]`. stdout을 파싱해 판정한다(`EXIT=n`, `error TS\d+`, `problems (n errors`). `tsc && eslint` 복합 호출은 1 call / 2 kind로 센다.

**축5a — v2에서 신설. 쓰기를 포함하는 것이 요점이다.** v1에는 계측 밖 **편집**을 세는 축이 없었다. 편집을 bash로 빼면 축1~4 어디에도 걸리지 않는다.

```
heredoc > file        77
redirect > 소스파일    56
sed -i                18
git apply              1
파일 쓰는 스크립트 heredoc  91   (stdout만 내는 분석용 215건은 제외)
                    ─────
              합계   243        Edit/Write 4,689 대비 4.9%   [검증]
```

편집 20건 중 1건이 계측 밖에 있다. 포매터(`prettier --write` 등)는 사람의 변경 의도가 아니라 정규화이므로 분자에서 뺀다. 분석만 하고 파일을 안 여는 heredoc도 우회가 아니므로 뺀다 — 이 구분을 안 하면 분자의 대부분이 통계 스크립트로 오염된다.

이 축을 채택한 이유는 조작 방향이 대체로 계측 강화 쪽이기 때문이다. 점수를 올리는 주된 방법이 `cat`·`sed -i`·heredoc을 버리고 Read/Edit/Write를 쓰는 것이다.

**단, 역방향 레버가 하나 있다.** 임시 경로 예외를 악용해 `2>/tmp/x.log`를 덧붙이면 bash 편집이 축에서 사라진다 `[검증]`. 그래서 예외 판정을 명령 전체가 아니라 **쓰기 대상 경로**에만 적용한다. 명령 전체에 걸면 `console.log(`가 들어간 편집이 조작 의도 없이도 통째로 빠진다.

**축5b — Grep·Glob은 분자에 넣는다.** v3까지 이 정의가 비어 있었는데, 선택만으로 축 값이 0.32~0.52로 갈린다 `[검증]`. `Bash(rg …)`를 `Grep` 도구로 바꾸기만 해도 모든 구간이 1.0이 되는 조작 경로가 생긴다. 축이 묻는 것은 "계측 도구를 썼나"가 아니라 "인덱스를 먼저 봤나"이고, Grep·Glob이 하는 일은 전수 스캔이므로 분자다. 계측 채널을 썼는지는 축5a가 따로 본다.

**축5b — v1 축5의 나머지 절반.** v1은 읽기 대체율(0.094)과 검색 대체율(0.514)을 행위수 가중 평균으로 묶었는데, 두 성분이 5.5배 벌어져 있어 큰 쪽만 보고하고 작은 쪽을 지우고 있었다. 분해한다.

### 5.3 폐기한 축과 사유

v1의 6축 중 5개가 폐기되거나 재정의됐다.

| v1 축 | 처분 | 사유 |
|---|---|---|
| 자율 완주력 | 폐기 | interrupt가 277세션 중 218개(78%)에서 0회 `[검증]`. 큐 개입을 합친 확장안도 split-half 0.281로 탈락 |
| 첫 시도 정확도 | 분해 | 재*읽기*는 축2로 승격. 재*편집*은 검증 실패. `is_error` 결합은 폐기 |
| 검증 성실도 | 정의 교체 | → 축3 |
| 컨텍스트 절제 | cache 부분 폐기 | `cache_read` 비율이 코퍼스 전체 0.9733으로 포화 `[검증]`. 중복 Read만 축2로 이월 |
| 규칙 준수 | **폐기 확정** | 5.3.1 |
| 결과 도달 | 폐기 | `pr-link` 중복은 제거 가능하나(3,946 → distinct 121 `[검증]`) 편집만 하고 커밋 없이 끝난 세션이 49% `[후보]`이고 정상(worktree 분리)과 비정상을 세션 단위로 못 가른다 |

#### 5.3.1 규칙 준수 축의 역설 — 폐기 확정

훅 차단은 "규칙을 어기려 했다"는 신호인데, 훅을 지우면 어겨도 잡히지 않아 점수가 올라간다. 방어를 없앨수록 좋아 보이는 값은 지표가 아니다.

v1은 "훅 커버리지로 정규화하거나 제외"라고 유보했다. v2는 **정규화도 하지 않고 폐기한다.** 차단 이벤트 기반 지표 3종(재발 누수·교정 수용·차단 후 적응력)을 전부 검토했는데 모두 세션당 분모 3건 내외라 축이 서지 않는다 `[후보]`.

대체는 축5a·5b다. 훅을 지워도 분자가 줄지 않으므로 "방어를 없앨수록 좋아지는" 형태는 아니다.

**다만 v3까지 쓴 "훅과 무관하므로 역설이 구조적으로 발생하지 않는다"는 문장은 과했고, 검토에서 반증됐다.** 훅에 막혀 실행되지 않은 Bash가 1,540건인데 그중 750건이 재귀 검색이었고 대부분 이 프로젝트 자신의 검색 게이트가 막은 것이다 `[검증]`. 차단 호출을 축에 넣으면 게이트가 잘 작동할수록 축5b가 나빠진다(0.394 → 0.479, +8.5%p). 축4도 같다(+7.1%p) — 훅이 복합 명령을 막고 에이전트가 순수 명령으로 재시도하면 그 재시도가 "같은 검증 두 번"으로 잡힌다.

**따라서 `denial_kind`가 있는 호출은 모든 축에서 제외한다.** 실행되지 않은 것은 행동이 아니다. 차단 건수는 별도로 세어 뷰 B에 보낸다.

### 5.4 육각형 배치

12시부터 시계방향. 상반부는 규율, 하반부는 낭비 억제다.

```
              ① 읽기 범위 규율
                     ▲
   ⑤b 인덱스우선 ◀         ▶ ③ 검증 신선도
                                
   ④ 공회전절제 ◀          ▶ ⑤a 계측채널
                     ▼
              ② 읽기 왕복 절제
```

| 대립쌍 | 성립 여부 | 근거 |
|---|---|---|
| ① ↔ ② | **성립** | 크기 통제 후 편상관 +0.407 `[후보]`. 축1을 올리려 잘게 쪼개면 재Read가 늘어 축2가 내려간다 |
| ③ ↔ ④ | **성립** | 편집마다 tsc를 붙이면 축3이 오르고 축4가 내려간다. 계산식 수준에서 자명 |
| ⑤a ↔ ⑤b | **성립하지 않음** | 같은 계열의 서로 다른 면이지 서로를 억제하지 않는다 |

세 번째 쌍이 약하다는 것을 문서에 남긴다. 부분 방어는 있다 — 5a를 올리려 Read를 남발해 분모를 부풀리면 축1·2가 동시에 내려간다. 그러나 **5b를 올리려 qmd·graphify를 무의미하게 남발하는 경로는 현재 어느 축도 잡지 못한다.** 육각형에서 가장 약한 자리다.

그럼에도 마주보게 두는 이유는 판독 규칙 때문이다. 상반부/하반부로 갈리면 찌그러진 방향만 보고 "규율이 약한가, 낭비가 많은가"를 바로 읽을 수 있다. 5a·5b를 인접에 붙이면 도구 사용 계열이 한쪽 날개로 몰려 모양이 계열 편향으로 왜곡된다.

### 5.5 정의의 SSoT는 산문이 아니라 코드다

v2에서 새로 넣는 원칙이다. **v1 수치 중 최소 4개가 재현되지 않았다.**

| 항목 | v1 기재 | 재측정 | 원인 |
|---|---|---|---|
| 축2 재Read율 | 16.6% | 8.92% `[검증]` | 정의와 수치가 다른 것을 가리킴 |
| 축3 분모 | 197 | 206~290으로 갈림 `[후보]` | 커밋 segment 경계와 코드 확장자 집합 미고정 |
| 축1 준수율 | 0.7992 | 0.751 `[후보]` | no-op 가드 경계 조건 차이 |
| 축5 성분 | 0.094 / 0.514 | 0.179 / 0.655 `[후보]` | 소스읽기·재귀검색 정규식 미고정 |

분모 971(축1)처럼 여러 측정이 일치한 값도 있다. 갈리는 것은 **판정 경계가 산문으로만 적힌 항목**이다.

따라서 지표 계산기에서 다음을 코드로 고정하고, 문서는 그 코드를 가리키기만 한다. 실제 위치는 `packages/core/src/definitions.ts`(축 상수·no-op 가드·stdout 판정)와 `packages/core/src/bash.ts`(명령 분류)다.

- 소스 파일 확장자 집합
- 재귀검색으로 볼 명령 패턴
- bash 파일 쓰기로 볼 패턴, 그리고 포매터 예외
- 커밋 segment 경계 정의
- verifier로 볼 명령과 stdout 성패 패턴

예외 목록은 **의미로 정의**한다("포매터"). 목록 자체가 조작 표면이 되기 때문이다 — 한 검증에서 allowlist 구성만 바꿔도 지표가 50% 상대 변동했다 `[후보]`. 목록을 바꾸면 그 이력을 뷰 B에 남긴다.

### 5.6 축별 성장 가이드

각 축에 "할 것"과 "하지 말 것"을 짝지어 둔다. 하지 말 것은 전부 점수는 오르는데 품질은 안 오르는 처방이다.

**축1 읽기 범위 규율**
- 할 것: 스킬 진입 시 컨텍스트 선주입. 재읽기 상위 파일이 곧 "미리 넣었어야 할 컨텍스트" 목록이다. 위임 brief 필수 요소에 **읽을 라인 범위**를 추가한다(현재 도구명과 호출 순서만 있다). 200줄 초과 레퍼런스 문서는 규칙을 고치지 말고 파일을 쪼갠다.
- 하지 말 것: `PreToolUse:Read`로 `limit` 강제 주입. `limit: 2000`은 no-op인데 부분읽기로 집계되고, 강제하면 chunk 순회로 대응해 축2만 나빠진다.

**축2 읽기 왕복 절제**
- 할 것: `PostToolUse:Edit` 훅이 편집한 hunk의 전후 3줄을 반환하게 바꾸면 편집 후 재Read가 불필요해진다. 같은 파일 3회 이상 재방문 세션을 뷰 B에 띄우고 그 세션의 스킬을 본다 — 특정 스킬에 몰려 있으면 그 SKILL.md의 단계 순서가 잘못된 것이다.
- 하지 말 것: 축1을 낮춰서(통째로 읽어서) 왕복을 줄이기.

**축3 검증 신선도**
- 할 것: 게이트를 커밋 시점으로 옮긴다. `PreToolUse:Bash`에서 `git commit`을 잡아 마지막 편집 이후 verifier가 없으면 차단하되, **대안 경로를 문장으로 지정**한다. 대안 명시 여부가 재발률을 가른다 `[후보]` — 대체 경로를 준 게이트는 재발 0.04, 금지만 통보한 게이트는 0.88.
- 하지 말 것: "항상 tsc를 돌려라"를 규칙에 넣기. stale은 "안 했다"가 아니라 "하고 나서 또 고쳤다"라 검증 횟수를 늘려도 원인을 안 건드린다.

**축4 검증 공회전 절제**
- 할 것: 스킬의 검증 스텝을 개별 나열 대신 `tsc && eslint && prettier --check` 단일 명령으로 못박는다. 파이프를 걷어낸다 — verifier에 `; echo "EXIT=$?"`를 요구하는 훅은 **조작 방향이 없는 드문 안전한 훅**이다(점수는 stdout 파싱으로 매기므로 exit code 노출이 점수를 올리지 않는다).
- 하지 말 것: 검증 횟수 상한을 훅으로 걸기. 수정 후 재검증까지 막힌다.

**축5a 계측 채널 준수**
- 할 것: 소스 읽기를 Read로, 파일 쓰기를 Edit/Write로 되돌린다. 프로젝트 규칙에 이미 있는 항목이므로 규칙이 아니라 집행이 빠진 것이다. 분석용 heredoc과 파일 쓰기용 heredoc을 분자 판정에서 구분한다.
- 하지 말 것: **예외 목록을 넓혀 점수 올리기.** 명령을 `&&`로 이어붙여 Bash 호출 수를 줄이는 것도 금지다 — 축3·4·5b가 동시에 실명한다.
- **편집을 subagent에 위임해 분모 밖으로 빼는 레버는 부분적으로 닫힌다.** `toolStats.editFileCount`가 기록되므로 축5a 분모에 subagent 편집 건수를 더한다(9절). 다만 subagent 내부의 bash 쓰기는 `bashCount`에 섞여 분자로 못 뽑으므로 **완전히 닫히지는 않는다.** 남는 구멍은 6.1의 커버리지 배지로 표시한다.

**축5b 인덱스 우선 탐색**
- 할 것: 검색 대체가 읽기 대체보다 나쁘다. `pre-code-search-qmd-reminder.sh`의 matcher가 `grep -r`·`rg`는 잡고 `find … -name`은 놓치는지부터 확인한다. 그리고 시스템 프롬프트가 아니라 **스킬 본문에 대체 경로를 쓴다** — 금지만 있고 대안이 없는 규칙은 재발률이 높다.
- 하지 말 것: `cat`/`sed`를 전면 차단하기. 차단하는 순간 그 규칙은 정의상 축5에서 빠져 "훅이 지탱하는 준수"로 이동하고, 축은 관측 범위를 잃는다. 축5의 존재 이유는 **훅을 걷어냈을 때 남는 준수**를 보는 것이다.

## 6. 뷰

| 뷰 | 답하는 질문 | 표현 | 상태 |
|---|---|---|---|
| B 누수 진단기 | 어디서 새는가 | 임계 초과 항목 + 근거 세션 ID | **구현·사용 중** |
| A 스코어카드 | 어느 방면이 강하고 약한가 | 구간 대비 delta 육각형 | 보류 (8.1) |
| C 개입 효과 | 내가 넣은 훅·스킬이 효과가 있었나 | 지표 시계열 × config 커밋 시점 | 보류 (8.1) |

**뷰 B만 남긴 이유는 안정성을 요구하지 않기 때문이다.** 비율이 아니라 건수와 근거 세션을
내므로, 축이 시간축에서 흔들려도 "이 세션에서 이 파일을 8번 다시 읽었다"는 사실은 그대로다.
뷰 A·C는 구간 간 비교가 성립해야 하는데 그 전제가 무너졌다.

뷰 C는 config 레포의 커밋 타임스탬프와 세션 타임스탬프를 정합해 도입 전후를 비교한다.

축3은 조작저항이 낮으므로 뷰 B에 **verifier 연쇄 실행 비율**을 함께 띄운다. `tsc && eslint && test`를 훅으로 강제하면 행동은 안 바뀌는데 축3이 0.664 → 0.942로 오른다 `[후보]`. 상승이 행동 변화인지 명령 구성 변경인지 구분할 수 있어야 한다.

### 6.1 계측 커버리지 배지 (점수 축 아님)

subagent 위임과 명령 이어붙이기는 **어떤 축으로도 막을 수 없다.** 관측 자체가 사라지기 때문이다. 축으로 만들면 다시 조작 대상이 되므로 비점수 배지로 처리한다.

```
관측 가능    = Read + Edit + Write
계측 밖      = bash 읽기 + bash 쓰기
불투명       = Σ toolStats.totalToolUseCount   (subagent 내부, 건수만 보임)

커버리지 = 관측 가능 / (관측 가능 + 계측 밖 + 불투명)
```

`toolStats` 덕분에 분모의 subagent 몫을 **호출 건수로 정확히** 넣을 수 있다(9절). v2 초안은 `Agent` 호출 수(269)를 쓰려 했는데, 실제 내부 활동은 7,291건이라 27배 과소평가였다 `[검증]`.

배지는 점수화하지 않는다. 임계 미만인 구간은 **육각형 6칸 전체를 회색 처리해 "판정 불가"로 표시**한다. 커버리지가 낮으면 축 값이 좋아 보여도 그것이 행동인지 은닉인지 구분되지 않는다. 값을 그리는 것보다 그리지 않는 것이 정확하다.

### 6.2 뷰 B 전용 지표 (축이 아닌 것)

축으로는 이벤트가 희박하지만 진단으로는 유용한 것들이다.

- **동일 차단 재발** — 같은 게이트에 반복해서 걸리는 패턴. 한 세션에서 같은 게이트 22회 반복 같은 값이 나온다 `[후보]`
- **훅 메시지 품질 랭킹** — 게이트별 교정 수용률. 대안 경로를 문장으로 준 게이트가 재발률이 낮다
- **자기인증 게이트 누수** — 승인 마커를 스스로 `touch`하는 패턴. 축 점수가 오르는 구간에 이 카운터가 함께 오르면 개입이 아니라 우회로 표시한다
- **질의 채널 유실** — `AskUserQuestion` 실패 건. 한 측정에서 720건 중 103건(14.3%) 실패, 그중 한국어가 유니코드 이스케이프된 긴 페이로드에 집중 `[후보]`. 이건 지표가 아니라 하네스 버그 리포트다

## 7. 화면 표면

1단계는 상태바와 패널까지다.

```
상태바   한 줄 요약, 클릭하면 패널
```

Webview는 CSP 때문에 외부 CDN을 불러올 수 없다. 축 6개짜리 레이더는 SVG로 직접 그리는 편이 짧다. 파싱은 Extension Host에서 돌리지 않고 자식 프로세스로 분리한다.

### 7.1 육각형 시각 사양

레퍼런스는 사용자가 지정한 역량 레이더 형식이다. 구성 요소:

```
정육각형 그리드      중심에서 꼭짓점까지 얇은 축선 6개
동심 점선 육각형      5단계 눈금
굵은 외곽 실선        기준 계열
채워진 폴리곤         현재 계열, 반투명 옅은 채움 + 진한 외곽선
꼭짓점 원형 마커      6개
축 라벨              축 방향으로 회전 배치
```

**이 형식이 delta 설계와 맞는다.** 레퍼런스는 도형이 두 개(외곽선 + 채움)인데, 3.4절의 delta 비교가 정확히 2계열이다.

| 도형 | 담는 것 |
|---|---|
| 굵은 외곽선 | 기준 계열 = 직전 3구간 중앙값 |
| 채워진 폴리곤 | 현재 계열 = 이번 구간 |

레퍼런스에서 외곽선은 만점 경계지만, 여기서는 **기준 구간**이다. 따라서 현재 계열이 외곽선을 **넘을 수도 있다**. 넘는 방향이 개선이므로 폴리곤이 외곽선 밖으로 나가는 렌더링을 허용해야 한다. 눈금 상한은 만점이 아니라 두 계열의 최댓값에 여유를 준 값으로 잡는다.

6축 전부 "높을수록 좋음"이다(역수 축은 계산 단계에서 뒤집는다). 그래야 바깥으로 넓어지는 것이 개선으로 읽힌다.

축 라벨은 회전 배치라 길이를 쓸 수 있지만, 판독을 위해 축당 한 줄로 제한한다.

```
① 읽기 범위 규율      ② 읽기 왕복 절제      ③ 검증 신선도
④ 검증 공회전 절제    ⑤ 계측 채널 준수      ⑥ 인덱스 우선 탐색
```

값 옆에 그 구간의 **분모**를 함께 띄운다(3.4절). 구간 크기 편차가 2~28세션이라 분모를 숨기면 작은 구간의 튐을 실제 변화로 오독한다.

커버리지 미달 구간은 6칸 전체를 회색 처리한다(6.1절). 이때 두 계열 모두 회색으로 그리고 "판정 불가"를 표시한다.

### M0.5 재현성 게이트 (v2 신설)

v1은 타당성 게이트를 M2 직전에 뒀는데 그 순서로는 늦다. 검증 2라운드에서 **후보 14개 중 무사통과가 0건**이었고, 죽은 것들은 전부 "실측 근거가 붙은 그럴듯한 축"이었다. 그리고 5.5절대로 확정축의 수치조차 재현되지 않는다.

M1 이전에 축3·4·5a·5b에 대해 다음을 통과해야 한다.

1. **정의 고정 후 재산출** — 정의를 바꿨을 때 값이 2배 이상 흔들리지 않을 것
2. **포화 검사** — 세션별 p05~p95 스프레드가 `cache_read`를 죽인 0.069보다 유의하게 클 것
3. **분모 밀도** — **이벤트 예산 구간** 단위로 분모가 예산치를 채울 것. 세션 단위 기준을 쓰지 않는다. 세션당 median으로 재면 축1(3.0)·축5b(2.0)·축3(0.7)이 미달인데, 이건 축의 결함이 아니라 단위 선택의 결함이었다 (3.4절)
4. **split-half 신뢰도** 0.5 이상
5. **길이 교란** — 세션 길이·도구 수와의 spearman이 0.5 미만이거나 정규화안이 있을 것
6. **독립성** — 확정축 간 `|r| > 0.6`이 없을 것
7. **조작 시뮬레이션** — 조작 시 중앙값 변화 10% 이내

집계 단위는 세션이 아니라 **주(week)**를 1차로 한다. 축1·3·4는 세션당 이벤트가 얇다(축3은 코드 커밋 197건 / 276세션).

### 8.1 M0.5 게이트 결과 (2026-07-30 실측)

`scouter gate`로 확정 6축에 돌렸다. 닫힌 구간 29개 기준.

| 항목 | 통과 | 비고 |
|---|---|---|
| 포화 | 6/6 | 스프레드 0.29~0.50. `cache_read`를 죽인 0.069보다 훨씬 크다 |
| 분모 밀도 | 6/6 | 구간당 median 10~314. 예산 벡터가 제대로 작동했다 |
| 길이 교란 | 6/6 | 세션 수와의 spearman 전부 `|rho| < 0.2` |
| 축 독립성 | 15쌍 전부 | `|rho| <= 0.6`. 같은 정보를 두 번 그리지 않는다 |
| split-half | **0/6** | 0.015 ~ 0.261, 축2는 −0.344 |
| **구간 안정성** | **0/6** | **lag-1 자기상관 −0.10 ~ 0.27** |
| 조작 저항 | 1/4 | 축5b 71.2p, 축5a 18.5p, 축4 17.5p 이동 |

**집계 단위 설계는 맞았다.** 이벤트 예산 구간이 분모를 채웠고(3.4절 의도대로) 축끼리 중복도
없다. 무너진 것은 축의 시간적 안정성이다.

#### 왜 치명적인가

delta 표시(3.4절)의 전제는 "직전 3구간 중앙값이 기준선이 된다"는 것이다. 그런데 이웃 구간이
서로를 예측하지 못하면 기준선 자체가 잡음이고, 화면의 모든 화살표가 잡음이 된다.

표본 부족이 아니다. 구간을 2·3·4개씩 병합해 창을 키워도 오르지 않았다 `[검증]`:

```
축              k=1     k=2     k=3     k=4
읽기 범위      -0.055  -0.376  -0.106  -0.143
검증 신선도     0.266  -0.239   0.254   0.620
계측 채널       0.075  -0.728  -0.268  -0.814
읽기 왕복       0.143  -0.239   0.244   0.075
검증 공회전    -0.103  -0.303  -0.546  -0.591
인덱스 우선    -0.100  -0.184   0.093  -0.005
```

#### 조작 저항 — 리뷰 예고가 실측으로 확인됐다

축5b는 **행동을 하나도 바꾸지 않고 `Bash(rg …)`를 `Grep` 도구로 갈아끼우기만 해도**
중앙값이 71.2p 오른다. 축5a·축4도 17~19p다. 3.2절이 경고한 "가장 싼 개선책이 대개 조작"의
가장 선명한 사례다.

#### 게이트 방법 자체를 두 번 고쳤다

측정 결과를 믿기 전에 측정 방법을 의심해야 했다.

1. split-half를 구간 안에서 **순서대로 번갈아** 갈랐더니 축2가 −0.782로 나왔다. 세션이
   시간순이라 큰 구현 세션과 짧은 확인 세션이 번갈아 오는 구조가 상관으로 잡힌 것이다.
   세션 아이디 해시 분할로 바꿨다.
2. 반쪽이 세션 한둘이 되면 비율이 통째로 튄다. 세션 6개 이상 구간만 쓰도록 제한했다.

두 수정 후에도 결론은 같았다. 방법 문제가 아니라 축 문제다.

#### 결정

뷰 A·C를 보류하고 뷰 B만 남긴다(6절). 축을 더 만지지 않는 이유는, 누적 후보 32개 중
14건을 적대적으로 검증해 무사통과가 0건이었고 이번에 확정축까지 전부 떨어졌기 때문이다.
"그럴듯한 축을 더 찾는" 경로는 이미 두 번 실패했다.

다음에 필요한 것은 축이 아니라 **라벨**이다. 지금 축들은 그럴듯해서 고른 것이고, 좋은 세션과
상관된다는 근거가 없다. 뷰 B를 실사용하며 세션 라벨을 모으고, 그 라벨로 M1.5를 돌린 뒤에
축 재설계를 판단한다.

### M1.5 라벨 타당성 게이트

1. 세션 30개를 수동으로 좋음/나쁨 라벨링한다. 당사자 기억이 남아 있는 동안 해야 한다.
2. 각 지표가 라벨과 상관되는지 확인한다.
3. 상관이 없는 지표는 폐기한다.

라벨 대상은 **실행 모드로 균형 표집**한다. headless와 대화형을 섞어 뽑지 않으면 라벨 상관이 실행 모드 상관으로 오염된다. 다만 3.1절대로 현재 headless 세션이 거의 없으므로, 표집 전에 축적이 필요하다.

**축이 3개만 남아도 진행한다.** 6개를 채우려고 억지 지표를 만들지 않는다. M0.5에서 축5a가 떨어지면 5a·5b를 축5로 재합성하고 5축 오각형으로 M2에 진입한다. 두 라운드 연속 전패가 나온 상황에서 **모양 요구가 축 탐색을 끌고 가는 것이 가장 큰 실패 요인**이다.

## 9. 알려진 사각지대

- **subagent 사각지대는 없다. 트랜스크립트가 디스크에 통째로 남는다.** v2·v3이 두 번 틀렸다. subagent 기록은 세션 디렉토리 아래 `subagents/`와 `workflows/` 안에 별도 파일로 쌓이고, 부모와 같은 `sessionId`에 `isSidechain: true`, `agentId`를 달고 있다 `[검증]`. 전수 스캔 결과 도구 호출 56,109건 중 **23,898건(43%)이 subagent 파일에 있었다** `[검증]`. 재귀 스캔으로 부모 세션에 합쳐 세므로 "위임하면 분모가 비어 점수가 오르는" 구멍이 닫힌다. `toolStats` 집계치는 트랜스크립트가 없는 세션의 폴백으로만 쓴다(둘 다 쓰면 이중 계상).
- **계측 밖 편집이 존재한다.** bash 기반 파일 변형 243건, Edit/Write 4,689 대비 4.9% `[검증]`. 축5a가 이걸 재지만, 축5a 자체가 아직 미검증이다.
- **세션 경계와 작업 경계가 다르다.** 한 세션에 여러 작업이, 한 작업이 여러 세션에 걸친다.
- **headless 층이 표본에 없다.** `entrypoint`가 `claude-vscode` 274 / `sdk-cli` 2 `[후보]`. 6축 전부가 대화형에서만 검증됐다.
- **`pr-link`가 중복 기록된다.** 3,946행 → distinct 121 `[검증]`.

### 반복 확인된 실패 패턴

새 축을 제안할 때 이 다섯 개를 먼저 확인한다.

1. **세션 길이 지배** — 값이 세션 길이에 단조 지배되면 축이 아니라 길이의 별칭이다
2. **분모 역설** — 분모가 사라지면 만점이 되는 구조
3. **포화** — 스프레드가 없으면 백분위를 내도 노이즈만 남는다
4. **이벤트 희박** — 집계 단위당 분모 median 3 이하면 축이 서지 않는다
5. **분자 오염** — 분자에 의도와 무관한 항목이 섞이면 다른 것을 재게 된다
